## Какой язык используется

**Python 3.10+** — язык реализации; проверено на **Python 3.14.5**.
Достаточно стандартной библиотеки, установка пакетов не требуется.
Python исполняется интерпретатором, отступы определяют блоки, типы объектов
выбираются во время исполнения. Аннотации `str`, `int`, `list[int]`,
`int | None` документируют типы и не заменяют проверки данных.

Основной синтаксис, который нужно знать:

- `def` — функция, `class` — класс; `self` — объект, у которого вызывают метод.
- `dict` хранит ключи и значения; AST состоит из словарей, списков и простых значений.
- `set` — множество; `frozenset` — неизменяемое множество, пригодное как ключ словаря.
- `None` — отсутствие значения, например отсутствующий контракт или ветка else.
- `@dataclass(frozen=True)` создаёт неизменяемую запись Token/Rule.
- `@property` делает `current()` доступным как `parser.current`.
- `@lru_cache(maxsize=1)` сохраняет построенный ДКА для повторных вызовов.
- `*items` распаковывает элементы, `**fields` — именованные поля словаря.
- `left, right = ...` распаковывает пару; `text[a:b]` берёт срез без позиции b.
- `raise` сообщает об ошибке, `try/except` перехватывает её.
- `r"..."` сохраняет обратные слеши для собственного парсера регулярных выражений.
- Включения `[... for ...]` и `{... for ...}` строят коллекции.
- `if __name__ == "__main__"` отделяет запуск CLI от импорта модуля.

**Funny** — входной учебный язык. Он описывает функции, целые числа, массивы,
ветвления, циклы, контракты, формулы и кванторы. HW2 выделяет структуру программы.
Исполнение, типы, объявление имён, неизменяемость параметров и число возвращаемых
значений проверяются следующими этапами, а не этим парсером.

## Запуск без лишних файлов

Команды выполняются из корня **рабочей копии ветки `codex/hw2`**:

```powershell
cd homeworks/hw2
python --version
python -B -m unittest -v test_parser.py
python -B parser.py --text 'function f(x:int) returns r:int {r=x+1;}'
python -B parser.py --file ../../project/examples/step01/good_basic.funny
```

На macOS используйте `python3` вместо `python` в этих командах.

`-B` запрещает запись `__pycache__`. Тесты и разбор программ выводят результат
в терминал и не создают файлов. В тестах выводятся имена 26 методов со статусами
`ok` и итоговое `OK`; отдельные входы обозначены через `subTest`.

Ошибка с позицией и восстановление:

```powershell
python -B parser.py --text 'f() returns r:int {r=; x=2;}'
```

В JSON будет синтаксическая диагностика на `;` (строка 1, столбец 22,
смещение 21), а в частичном AST сохранится присваивание `x=2`.
Код завершения: `0` при успехе, `1` при диагностике/ошибке чтения,
`2` при неправильном использовании CLI. Нужно передать ровно один из
`--text` и `--file`. Файл читается как UTF-8 без преобразования переводов строк.

Для следующих HW можно использовать API из этой папки:

```python
from parser import parse

result = parse("f() returns r:int {r=1;}")
if result["diagnostics"]:
    print(result["diagnostics"])
else:
    tree = result["ast"]
```

## Конвейер и лексер

```text
правила токенов → НКА Томпсона → ДКА подмножеств → Хопкрофт
                                                     ↓
текст → токены с позициями → рекурсивный спуск → AST + диагностика
```

Повторно используются 47 правил HW1: 20 ключевых слов, IDENT, INT, WS,
COMMENT и 23 оператора/разделителя. НКА содержит 295 состояний, ДКА — 125,
минимальный ДКА — 122; старт 0, ловушка 1. Автомат строится при первом
вызове `machine()` и сохраняется в памяти процесса.

Сканер выбирает длиннейшее совпадение, а при равной длине — первое правило.
Поэтому `if` — IF, `ifx` — IDENT, `==` — EQ, `//...` — COMMENT.
`int` получает TYPE_INT, а число — INT. WS/COMMENT пропускаются, но их символы
учитываются при вычислении позиций. После последнего токена добавляется EOF.

| Правило | Выражение/поведение |
| --- | --- |
| IDENT | `[A-Za-z_][A-Za-z0-9_]*` |
| INT | `0` или `[1-9][0-9]*`; дополнительный запрет соседней цифры после одиночного 0 |
| WS | `[ \t\r\n]+`, skip |
| COMMENT | `//[^\r\n]*`, skip |
| Ключевые слова | Отдельное правило на каждое слово, раньше IDENT |
| Операторы | Буквальные лексемы из SYMBOLS с экранированием метасимволов |

Алфавит — ASCII. `_` разрешён согласно HW1/P01, хотя корневая спецификация
описывает идентификаторы только из букв и цифр. `00`/`01` запрещены, `-42`
разбирается как отдельные MINUS и INT. Non-ASCII — ошибка даже внутри комментария.
Unicode-стрелка `→` из некоторых примеров не принимается; нужна ASCII-запись `->`.
Исходные примеры курса при тестировании не исправляются.

Позиции: `offset` начинается с 0; `line` и `column` — с 1.
CRLF считается одним переводом строки; одиночные CR и LF тоже завершают строку.
Табуляция увеличивает столбец на один символ. Сначала строится список начал строк,
затем двоичный поиск `bisect_right` переводит смещение в строку и столбец.
У EOF тоже есть позиция, поэтому незакрытая скобка в конце файла диагностируется.

## Грамматика, LL-разбор и приоритеты

Полная грамматика записана в [grammar.ebnf](grammar.ebnf). Вариант реализации —
предиктивный рекурсивный спуск ветки P03. Для выражений удалена левая рекурсия,
для определений и присваиваний вынесены общие префиксы. Список параметров
разбирается один раз; после него `=>` выбирает формулу, а `requires`/`returns`
выбирают функцию. После IDENT в присваивании выбирается индексируемая,
кортежная или обычная левая часть.

Синтаксис из материалов согласован так:

1. Функция может начинаться как `f(...)`, так и `function f(...)`: первая
   форма в спецификации и корпусе, вторая в HW2/P03. Префикс формулы запрещён.
2. Параметры и возвраты имеют обязательные типы `int`/`int[]`. В `uses`
   аннотация необязательна. `returns` обязателен и содержит хотя бы одно имя.
3. `requires`, `ensures`, `invariant` необязательны. Допускаются пустые
   предложения, если следующий токен не начинает выражение. Для пустого
   ensures/invariant перед присваиванием используйте блок `{...}`:
   `ensures r=1;` неоднозначно, IDENT жадно начинает выражение контракта.
   Отсутствующий и пустой контракт представлены `null`; будущая семантика
   задаёт requires/invariant=true, ensures=false согласно спецификации.
4. Формула имеет тело после `=>`; завершающая `;` необязательна для совместимости
   с EBNF спецификации и примерами. В формуле разрешена ASCII-импликация.
5. Общая грамматика выражений используется в арифметике, условиях и предикатах.
   Парсер может построить AST для `if(42)` или `true+1`; проверка совместимости
   типов относится к HW3. Кванторы/формулы вне предикатов также отклонит HW3.
6. Индексация может быть повторной и применяться к результату вызова.
   Это синтаксическое расширение; допустимость типов определяется позднее.
7. `else` относится к ближайшему `if`. Пустой модуль, лишняя `;`, самостоятельный
   вызов как оператор и цепочка сравнений `a<b<c` являются ошибками.

### Устранение левой рекурсии и FIRST/FOLLOW

Для объяснения на защите выделим арифметическое ядро без вызовов и индексов:

```text
E  → T E'
E' → + T E' | - T E' | ε
T  → U T'
T' → * U T' | / U T' | ε
U  → - U | F
F  → IDENT | INT | ( E )
```

Так преобразуется исходная левая рекурсия `E → E + T | E - T | T`.
В реализации E соответствует `additive`, T — `multiplicative`, U — `unary`.
Хвосты E'/T' реализованы циклом `chain()`, который собирает дерево **слева**.

Для отдельного запуска E с завершающим EOF:

| Нетерминал | FIRST | FOLLOW |
| --- | --- | --- |
| E | IDENT, INT, `(`, `-` | `)`, EOF |
| E' | `+`, `-`, ε | `)`, EOF |
| T | IDENT, INT, `(`, `-` | `+`, `-`, `)`, EOF |
| T' | `*`, `/`, ε | `+`, `-`, `)`, EOF |
| U | IDENT, INT, `(`, `-` | `*`, `/`, `+`, `-`, `)`, EOF |
| F | IDENT, INT, `(` | `*`, `/`, `+`, `-`, `)`, EOF |

Ключевые клетки LL(1)-таблицы: для E по IDENT, INT, `(` или `-` выбирается T E';
для E' по `+` выбирается + T E', по `-` — - T E', по `)` или EOF — ε.
Аналогично T' выбирает `*` или `/`, а на `+`, `-`, `)`, EOF — ε.
U выбирает `- U` только по MINUS, F — по IDENT/INT/LPAREN. Конфликтов нет.
В полной подграмматике выражений к FIRST добавляются bool, вызовы, кванторы;
FOLLOW расширяется разделителями аргументов, индексов, контрактов и операторов.

**Ограничение утверждения LL(1):** общая грамматика с необязательным `else`
не имеет бесконфликтной таблицы для данной записи: ELSE попадает и в FIRST
ветки else, и в FOLLOW пустой ветки. Здесь конфликт разрешается явно:
внутренний вызов `statement()` потребляет ближайший ELSE первым.
Аналогично для необязательных пустых контрактов выбирается выражение, когда
токен входит в EXPR_START. Поэтому работа — рекурсивный LL-разбор с указанными
политиками; утверждение о LL(1) относится к подграмматике выражений.
Это те самые неоднозначности, которые P03 предлагает разрешить стратегией.

## AST и функциональное обновление массива

API `parse(text)` возвращает `{"ast": ..., "diagnostics": [...]}`.
Каждый узел AST содержит `type` и `pos={offset,line,column}`.
Позиция составного выражения указывает на его оператор; у Index — на `[`,
у Function — на `function` или имя. Скобки не образуют отдельный узел.

| Узел | Основные поля |
| --- | --- |
| Module | definitions |
| Function | name, params, returns, requires, ensures, locals, body |
| Formula | name, params, predicate |
| VarDecl | name, annotation (`int`, `int[]` или null) |
| Block | statements |
| Assign | target (Name), value |
| TupleAssign | targets (список Name), value (Call) |
| ArraySet | array (Name), indices (список выражений), value |
| If | condition, then, otherwise (узел или null) |
| While | condition, invariant (узел или null), body |
| Assert / Assume | predicate |
| Binary | operator, left, right |
| Unary | operator, operand |
| Integer | value — текст цифр, а не преобразованное Python int |
| Boolean | value — true/false |
| Name | name |
| Call | name, args |
| Index | array, index |
| Quantifier | quantifier, variable (VarDecl), predicate |

Текст цифр сохраняет большие литералы без ограничений преобразования Python int;
проверка диапазона/преобразование принадлежит семантическому этапу.
Различить функцию и ссылку на формулу по одному вызову нельзя: Call будет
уточнён после построения таблицы имён в HW3.

Присваивание `a[i]=v` обессахаривается сразу:

```text
Assign
  target: Name(a)
  value: ArraySet
    array: Name(a)
    indices: [Name(i)]
    value: Name(v)
```

ArraySet — внутренняя операция копирования, не пользовательский вызов `set`.
При последующем исполнении она читает исходный массив, вычисляет индексы
слева направо один раз, затем правую часть один раз и создаёт копию по пути
индексов. Для `a[i()][j()]=v()` AST содержит по одному вызову i, j, v.
Так не возникает повторного вычисления индексов при наивном разворачивании
вложенных `set(a,i,set(a[i],j,v))`. Само исполнение и копирование памяти в HW2
не реализуются: здесь фиксируется семантика внутреннего узла для будущего IR.

## Ошибки и режим паники

Диагностика содержит `phase` (`lexical`/`syntax`), `message`, `offset`, `line`,
`column`. Лексическая ошибка завершает разбор: токены для парсера не готовы,
поэтому ast=null. При синтаксических ошибках возможно частичное дерево.
Его нельзя передавать на кодогенерацию, пока список diagnostics не пуст.

В блоке после ошибки пропускаются токены до `;`, `}`, EOF или начала следующего
оператора. `;` потребляется, `}` сохраняется для закрытия текущего блока.
Если ошибочный разбор не сдвинулся, режим паники принудительно потребляет токен,
кроме защищённых `}`/EOF. Это обеспечивает прогресс. Например, отсутствие `;`
перед следующим присваиванием не уничтожает это следующее присваивание.

На уровне модуля поиск следующего определения учитывает глубину фигурных
скобок; вне блока ищется FUNCTION либо IDENT перед LPAREN. Это эвристическое
восстановление: при сильно повреждённой структуре возможны каскадные ошибки,
а незавершённое определение может быть исключено целиком. Закрывающие токены
при ошибке выражения не потребляются заранее. Чрезмерная вложенность возвращает
читаемую диагностику вместо traceback RecursionError.

- Все 128 ASCII-кодов внутри комментария, non-ASCII и ведущие нули.
- 500 повреждённых строк с seed=2026: проверяется завершение и ограниченность
  числа сообщений; очень глубокие скобки тоже возвращают диагностику.
- 42 неизменённых примера курса: 20 разбираются, 21 отклоняется лексически
  из-за non-ASCII, 1 — синтаксически. Семантически плохие ASCII-примеры
  принимаются, если их синтаксис корректен.
- Реальные запуски CLI, JSON, входной файл, отсутствие/конфликт аргументов,
  ошибка чтения и коды завершения.

Полные ожидаемые входы и результаты находятся прямо в `test_parser.py`:
POSITIVE, NEGATIVE и явные словари ожидаемых деревьев. Отдельные snapshot-файлы
не создаются. `shape()` убирает только pos для сравнения структуры, а позиции
проверяются другими тестами. Деревья не вычисляются тем же парсером «для эталона».

Короткое объяснение своими словами:

> Лексер из HW1 распознаёт токены через минимальный ДКА. В HW2 я добавил

> и выражениям. Приоритеты задаются уровнями функций, левую ассоциативность
> даёт цикл, правую — рекурсивный разбор правой части. AST хранит смысловую
> структуру без лишних скобок. При ошибке парсер сообщает координаты и ищет
> безопасную точку продолжения, сохраняя следующие корректные операторы.

На демонстрации показать grammar.ebnf, запустить тесты, разобрать
`1+2*3`, `8-3-1`, `a->b->c`, вложенные if/else и обновление массива.
Потом показать два независимых синтаксических сбоя в одном блоке и сохранение
следующего корректного оператора. Завершить форматом AST/API для HW3.

| Что могут спросить | Что ответить |
| --- | --- |
| Чем лексер отличается от парсера? | Лексер выделяет токены из символов; парсер связывает токены по грамматике в дерево. |
| Почему одного ДКА недостаточно? | Произвольная вложенность скобок требует стека; в рекурсивном спуске это стек вызовов. |
| Что значит LL(1)? | Чтение слева направо, левосторонний вывод, выбор продукции по одному токену просмотра. |
| Вся ваша грамматика строго LL(1)? | Выражения — да; dangling else и пустые контракты имеют явно задокументированные правила выбора. |
| Что такое FIRST/FOLLOW? | FIRST — возможные первые терминалы; FOLLOW — возможные следующие терминалы; для ε используют FOLLOW. |
| Почему опасна левая рекурсия? | Рекурсивный спуск вызывает тот же нетерминал до потребления токена и зацикливается. |
| Как устранена левая рекурсия? | E→E+T\|T превращена в E→TE', E'→+TE'\|ε; в коде хвост разбирается циклом. |
| Почему цикл строит левую ассоциативность? | Предыдущий результат становится left следующего Binary. |
| Почему импликация правая? | Правая часть разбирается повторным вызовом expression, а не следующим шагом цикла. |
| Как разрешается общий префикс функции и формулы? | Сначала общий заголовок, затем выбор по => или returns/requires. |
| К какому if относится else? | К ближайшему незакрытому if; внутренний вызов statement увидит его первым. |
| Зачем EOF как токен? | Конец входа имеет вид и позицию; можно диагностировать незакрытые конструкции. |
| Почему колонка после таба растёт на 1? | Измеряются символы, а не ширина отображения редактора; это явно принятое правило. |
| Почему INT хранится строкой? | Парсер сохраняет лексему; величину и диапазон проверит семантика. |
| Почему if(42) принят? | Это проверка типа условия в HW3, а не формы выражения в HW2. |
| Зачем отдельный ArraySet? | Он фиксирует функциональное копирование и однократное вычисление индексов; это внутренний узел. |
| Что если функция возвращает два значения внутри арифметики? | Синтаксис вызова построится, число результатов проверяется после объявления функций. |
| Почему нельзя продолжить кодогенерацию по частичному AST? | В дереве отсутствуют повреждённые части, а diagnostics сообщает о незавершённой проверке. |
| Как не зациклиться на ошибке? | Продвигать токен, если парсер не сдвинулся, и останавливаться на ;/}/EOF или начале следующего оператора. |
| Почему не потребляется } в atom? | Он нужен для синхронизации и корректного закрытия блока. |
| Почему русский комментарий — ошибка? | По HW1 алфавит всего входа ASCII; пропуск комментария не расширяет алфавит. |
| Где возникает рекурсия? | Вложенные блоки/скобки, unary, not, implication и тела условных операторов. |
| Что изменилось относительно HW1? | Добавлены позиции, EOF, грамматика, AST и синтаксическая диагностика; автоматы переиспользованы. |

Нужно уметь вручную заполнить несколько клеток LL(1)-таблицы арифметического
ядра, нарисовать AST выражения, объяснить конфликт dangling else и проследить,
как меняется индекс токена при восстановлении после ошибки.

## Как читать test_parser.py

`POSITIVE` содержит именованные корректные входы; `NEGATIVE` — ошибочные.
`successful()` требует отсутствие диагностики; `value()` выделяет правую часть
присваивания для сравнения дерева выражения. `name`, `integer`, `binary` создают
эталонные словари вручную. `shape` удаляет только координаты.

Тестовые методы названы по проверяемому поведению: `test_exact_ast_snapshot`,
`test_arithmetic_precedence_associativity_and_unary`,
`test_boolean_precedence_and_right_associative_implication`,
`test_array_update_desugars_without_duplicating_index_calls`,
`test_panic_recovery_retains_following_statements_and_definitions` и остальные.
`assertEqual` сравнивает факт и ожидание, `assertRaises` требует исключение,
`subTest` подписывает отдельный вход. `subprocess.run` проверяет реальный CLI
с ограничением времени и с ключом -B. Все эталоны и тесты находятся в одном файле.
