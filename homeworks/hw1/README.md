## Как запускать

Из корня репозитория перейдите в папку задания:

```powershell
cd homeworks/hw1
python --version
python -B lexer.py
python -B -m unittest -v test_lexer.py
```

На macOS используйте `python3` вместо `python` в этих командах.

Ключ `-B` запрещает запись кэша `__pycache__`. Обычный запуск и тесты не создают
файлов результатов. Тесты выводят имена 18 проверок со статусом `ok`, затем `OK`.
Внутри проверок используются отдельные случаи `subTest`; при ошибке показываются
имя случая и входная строка. Ожидания записаны в коде тестов до сравнения результата.

Разобрать строку:

```powershell
python -B lexer.py --text 'x=42; // comment'
```

Результат:

```json
[["IDENT", "x"], ["ASSIGN", "="], ["INT", "42"], ["SEMICOLON", ";"]]
```

Разобрать файл UTF-8, сохранив различие CR, LF и CRLF:

```powershell
python -B lexer.py --file ../../project/examples/step01/good_basic.funny
```

Проверить ошибку числа с ведущим нулём:

```powershell
python -B lexer.py --text 'x=01;'
```

## Регулярные выражения и принятые правила

Вход — встроенный упорядоченный список `RULES` из 47 правил. Парсер поддерживает
конкатенацию, альтернативу `|`, скобки, повторения `*`, `+`, `?`, классы символов,
диапазоны и отрицательные классы. Приоритет операций: повторение, конкатенация,
альтернатива. Экранирование поддерживает `\t`, `\r`, `\n` и буквальное значение
экранированного символа, например `\(`. Это небольшой собственный диалект:
нет групп захвата, обратных ссылок, `\d`, `{m,n}`, wildcard `.` и якорей.
Неэкранированная точка рассматривается как обычный символ.

| Токен | Регулярное выражение | Действие |
| --- | --- | --- |
| Ключевое слово | Само слово, отдельное правило для каждого | Выдать токен |
| `IDENT` | `[A-Za-z_][A-Za-z0-9_]*` | Выдать идентификатор |
| `INT` | `0\|[1-9][0-9]*` | Выдать целочисленную лексему |
| `WS` | `[ \t\r\n]+` | Пропустить |
| `COMMENT` | `//[^\r\n]*` | Пропустить |
| Оператор/разделитель | Его буквальная запись с экранированием метасимволов | Выдать токен |

В строке таблицы для `INT` знак `|` означает альтернативу, а обратный слеш
перед ним нужен только для отображения Markdown-таблицы. В коде записано
`r"0|[1-9][0-9]*"`.

Ключевые слова:

```text
function returns uses requires ensures while if else assert assume
invariant length int true false not and or forall exists
```

Имена токенов — слова в верхнем регистре, например `FUNCTION`, `RETURNS`, `IF`.
Исключение: слово `int` получает `TYPE_INT`, чтобы отличаться от числового `INT`.
`length` выделено отдельно согласно HW1. Все ключевые слова стоят раньше `IDENT`.

Операторы и разделители:

| Запись | Токен | Запись | Токен |
| --- | --- | --- | --- |
| `(` | `LPAREN` | `)` | `RPAREN` |
| `[` | `LBRACKET` | `]` | `RBRACKET` |
| `{` | `LBRACE` | `}` | `RBRACE` |
| `,` | `COMMA` | `;` | `SEMICOLON` |
| `:` | `COLON` | `\|` | `PIPE` |
| `+` | `PLUS` | `-` | `MINUS` |
| `*` | `STAR` | `/` | `SLASH` |
| `==` | `EQ` | `!=` | `NE` |
| `<=` | `LE` | `>=` | `GE` |
| `<` | `LT` | `>` | `GT` |
| `=` | `ASSIGN` | `->` | `IMPLIES` |
| `=>` | `ARROW` | | |

Условия и материалы курса местами расходятся. Для этого решения зафиксированы
следующие решения:

1. **Подчёркивания разрешены** по HW1 и P01, хотя описания Funny в корне говорят
   об идентификаторах только из букв и цифр. `_`, `_x`, `a_b2` проходят тесты.
2. **Ведущие нули запрещены**: `0` допустимо; `00`, `01`, `00042` — ошибка.
   Само регулярное выражение `INT` недостаточно: сканер мог бы превратить `01`
   в два допустимых токена. Поэтому перед выдачей `INT("0")` сканер отдельно
   проверяет следующий символ. При экспорте эта политика тоже записывается.
3. Комментарий заканчивается на **CR или LF**, либо на конце файла. Так
   корректно обрабатываются LF, CRLF и одиночный CR, указанные в материалах.
4. **Весь вход ограничен ASCII**: кодовые значения `0..127`. Non-ASCII идёт
   в ловушку и вызывает ошибку, в том числе внутри комментариев. В 21 из 42
   примеров курса есть non-ASCII, преимущественно русские комментарии;
   тесты ожидают для них ошибку на первом таком символе. Остальные 21 пример
   сравниваются с независимым лексером. Исходные примеры не изменялись.
5. Лексер применяет **длиннейшее совпадение**, а при равной длине — первое
   правило. `if` — `IF`, `ifx` — один `IDENT`; `==` — один `EQ`;
   `//text` — комментарий, `/` — деление.
6. Знак числа — отдельный оператор: `-42` → `MINUS`, `INT`.
   `12abc` → `INT("12")`, `IDENT("abc")`; запрета такой границы в HW1 нет.
   Пробелы не являются обязательными разделителями токенов.
7. Пустая строка и только WS/COMMENT дают пустой список. Неизвестный символ
   вне комментария вызывает ошибку. Блоковые комментарии и строки в HW1
   не вводятся. Ограничение диапазона целых и синтаксис программы не проверяются.

## Как устроено решение

### 1. Построение НКА по Томпсону

НКА допускает несколько переходов по одному символу и ε-переходы,
которые не потребляют вход. В коде метка ε — `None`, метка символа — ASCII-код.
`edges[s][label]` хранит множество целевых состояний.

Парсер регулярного выражения сразу возвращает фрагмент `(start, end)`:

- Символ/класс: два состояния, переход по каждому разрешённому символу.
- Конкатенация AB: ε-переход из конца A в начало B.
- Альтернатива A|B: общий новый вход и выход, две ε-ветки.
- A*: обход A для нуля повторений и обратное ε-ребро для повторения.
- A+: такое же обратное ребро, но без обхода для нуля повторений.
- A?: обход для нуля повторений, без обратного ребра.

НКА всех правил подключаются к общему старту ε-переходами. Конец каждого
правила помечен его номером — приоритетом. Номер меньше — приоритет выше.
`closure(S)` находит все состояния, достижимые из S только по ε-переходам,
включая сами S. Множество посещённых состояний останавливает ε-циклы.
Токены, принимающие пустую строку, запрещены: иначе сканер мог бы не двигаться.

### 2. Построение ДКА методом подмножеств

Каждое состояние ДКА — множество одновременно возможных состояний НКА.
Начальное множество — ε-замыкание общего старта.
Для множества S и символа a вычисляется:

```text
move(S, a) = объединение всех переходов из состояний S по символу a
δ(S, a) = ε-closure(move(S, a))
```

Новые множества получают номера и добавляются в очередь обработки.
В реализации роль очереди выполняет список `subsets`: цикл по списку
доходит и до добавленных в его конец элементов.
Если в множестве есть принимающие состояния НКА, выбирается правило
с минимальным номером. Получается одно значение `accept[state]`.

Пустое множество — **ловушка**: из него по любому ASCII-символу снова
получается пустое множество. Оно явно добавляется в таблицу. Все 128 переходов
есть у каждого состояния. Non-ASCII обрабатывается `DFA.step()` и тоже
направляется в ловушку, без попытки индексировать таблицу за её пределами.

Для правил Funny все построенные состояния достижимы. В общем случае,
например для правила «любой ASCII», явная ловушка может быть недостижима
по ASCII; она всё равно нужна для non-ASCII, что отдельно проверяется.

### 3. Минимизация Хопкрофта

Сначала состояния разбиваются по **номеру принимающего правила**, включая
отдельную группу для `None`. Делить только на «принимающее/непринимающее»
нельзя: тогда можно ошибочно объединить `IDENT` и `INT`.

Далее берётся блок-разделитель A и символ a. По обратным переходам находится
X — множество состояний, переходящих по a в A. Каждый текущий блок Y делится
на Y∩X и Y\X, если обе части непусты. Если Y уже ждал обработки, он заменяется
двумя частями; иначе в список работы добавляется меньшая часть. Это правило
выбора разделителей Хопкрофта. Когда список работы пуст, различимые состояния
уже разделены. Из каждого блока берётся представитель для новой таблицы.

Сортировка блоков по минимальному номеру делает нумерацию воспроизводимой.
Старт и ловушка перенумеровываются через тот же словарь `owner`.
Минимальность здесь означает сохранение **меток токенов**, а не только
объединённого языка всех токенов. Поэтому уменьшение со 125 до 122 небольшое.

Это учебная реализация с множествами и просмотром блоков при каждом уточнении.
Классическая оценка O(|Σ|·n·log n) для оптимизированного Хопкрофта не обещается
для этих структур данных. Детерминизация в общем случае может создать до 2^m
состояний для НКА из m состояний.

### 4. Сканирование текста

С каждой новой позиции сканер запускает ДКА заново. `cursor` идёт вперёд,
а `last` запоминает последнюю принимающую позицию и правило. При попадании
в ловушку ASCII-символа сканер возвращается к `last`. Символ, который
не вошёл в токен, затем читается снова со старта следующего токена.
Если `last` нет — допустимый токен не найден, создаётся `LexError`.
Для non-ASCII ошибка немедленная, даже если раньше был принят COMMENT.
После проверки ведущего нуля токен выдаётся либо пропускается по `skip`.

Пример для `ifx==0`:

| Прочитано со старта | Последнее принятие | Что происходит дальше |
| --- | --- | --- |
| `i` | `IDENT("i")` | Продолжаем |
| `if` | `IF("if")` | Длины равны; ключевое слово приоритетнее IDENT |
| `ifx` | `IDENT("ifx")` | Более длинное совпадение заменяет IF |
| Следующий `=` | Сохраняется `IDENT("ifx")` | Ловушка для текущего токена; выдаём IDENT |
| `=` со старта | `ASSIGN("=")` | Продолжаем |
| `==` | `EQ("==")` | Длиннейшее совпадение |
| Следующий `0` | Сохраняется `EQ("==")` | Выдаём EQ и начинаем число |
| `0` | `INT("0")` | Конец входа; выдаём INT |

## Экспорт и переиспользование в T0/HW2

`serialize()` возвращает обычный словарь. Поля JSON:

| Поле | Смысл |
| --- | --- |
| `format` | Версия формата `funny-dfa-v1` |
| `alphabet_codes` | Колонки таблицы: коды 0..127 по порядку |
| `start` | Номер стартового состояния |
| `trap`, `outside_ascii` | Номер ловушки и переход для non-ASCII |
| `rules` | Упорядоченные правила с `kind`, `pattern`, `skip` |
| `accept` | Для каждого состояния: индекс правила либо `null` |
| `transitions` | `transitions[state][ASCII_code]` — следующее состояние |
| `scanner_policy` | Длиннейшее совпадение, первое правило, запрет ведущего нуля |

После сохранения `dfa.json` восстановить автомат можно так, находясь в этой папке:

```python
import json
from pathlib import Path
from lexer import DFA, Rule, tokenize

data = json.loads(Path("dfa.json").read_text(encoding="utf-8"))
dfa = DFA(data["transitions"], data["accept"], data["start"], data["trap"])
rules = tuple(Rule(**rule) for rule in data["rules"])
print(tokenize("if(x<=42)", dfa, rules))
```

Построение НКА и минимизация при таком запуске уже не требуются. Для интеграции
в другой лексер нужно перенести также политику сканирования, включая leading-zero:
сама таблица описывает распознавание **одного** токена, а не всю последовательность.
Можно переиспользовать непосредственно `build()` и `tokenize()` из Python.

```text

Start: 0; trap: 1; rules: 47; alphabet: 128 ASCII codes
```

Позиции строк/столбцов не добавлены, поскольку HW1 этого не требует.

Проверено: **18 тестовых методов, все проходят**. В них:

- 19 явно заданных положительных и 21 отрицательный случай с ожидаемыми
  токенами или смещениями ошибок; проверяются исходный и минимальный ДКА.
- Все 20 ключевых слов, их границы и все 23 оператора/разделителя.
- Каждый из 128 ASCII-кодов отдельно и внутри `//`-комментария.
- Non-ASCII, управляющие символы, EOF, CR/LF/CRLF, `_`, `00`, `01`, знак числа,
  соседние операторы, конфликт `INT`/`TYPE_INT`.
- Полнота таблиц, диапазоны целевых состояний, ловушка, достижимость.
- Точная эквивалентность исходного и минимального ДКА обходом произведения:
  для каждой достижимой пары совпадает принимающее правило и проверяются все
  ASCII-переходы. Это покрывает все ASCII-слова, а не только примеры.
- Независимое уточнение классов по Муру: все состояния минимального ДКА
  различимы по выходам и будущим переходам.
- Для 13 выражений: все слова длины 0..3 над десятисимвольным тестовым
  алфавитом плюс завершающий `z`. Сравниваются Python `re.fullmatch`,
  непосредственное исполнение НКА, ДКА и минимального ДКА.
- 500 воспроизводимых составных строк против независимого сканера на `re`.
- Все 42 примера курса с учётом ASCII-политики; JSON round-trip и CLI.

`re` используется **только в тестах** как независимый эталон. В `lexer.py`
нет вызовов готового движка регулярных выражений.

Некоторые показательные случаи:

| Ввод | Ожидание |
| --- | --- |
| `""`, `" \t\r\n"` | Пустой список |
| `"0"` | `INT("0")` |
| `"00"`, `"01"` | Ошибка на позиции 0 |
| `"_a a_b2"` | Два IDENT |

| `"int 42"` | TYPE_INT, INT |

| `"// @ 01"` | Пустой список |
| `"foo @ 42"` | Ошибка на позиции 4 |
| `"// я"` | Non-ASCII, ошибка на позиции 3 |

## Как защищать работу

Начать можно с такого объяснения своими словами:

> Я задаю правила токенов регулярными выражениями и строю для них общий НКА
> по Томпсону. Затем каждое множество возможных состояний НКА становится
> состоянием ДКА. Принимающее правило выбирается по приоритету. Хопкрофт
> объединяет состояния с одинаковым выходом и одинаковым будущим поведением.
> Сканер работает по минимальной таблице, выбирает длиннейший токен,
> пропускает пробелы/комментарии и сообщает о недопустимом входе.

Порядок демонстрации:

1. Показать `RULES`: входные выражения действительно идут в собственный парсер.
2. Запустить `python -B lexer.py`: назвать 295 → 125 → 122 и ловушку 1.
3. Разобрать `if ifx x==0;` и объяснить оба правила выбора токена.
4. Показать отрицательные `01`, `@` и non-ASCII, а также пропуск `//comment`.
5. Запустить тесты; выделить проверки эквивалентности и минимальности.
6. Показать экспорт JSON и объяснить, что его таблица пригодна следующему лексеру.

### Что нужно знать и что могут спросить

| Вопрос | Ответ |
| --- | --- |
| Что такое токен и лексема? | Токен задаёт категорию, например IDENT; лексема — конкретный фрагмент `count`. |
| Чем НКА отличается от ДКА? | У НКА может быть несколько вариантов перехода и ε-ребра; у полного ДКА для каждого символа ровно один переход. |
| Что такое ε? | Переход без чтения символа; это не пробел и не пустой ASCII-символ. |
| Зачем ε-замыкание? | Чтобы учитывать все состояния, достижимые без дополнительного ввода; нужно в начале и после каждого move. |
| Почему closure не зацикливается? | Каждое состояние добавляется в pending только при первом посещении. |
| Как Томпсон строит A*, A+, A? | Общее подключение фрагмента; обход отвечает за ноль повторений, обратное ребро — за повторение. |
| Почему вложенный парсер — рекурсивный спуск? | Каждый метод соответствует уровню грамматики выражения и вызывает более приоритетный уровень. |
| Зачем frozenset? | Подмножество должно быть неизменяемым и хешируемым, чтобы словарь узнавал уже построенное состояние. |
| Как выбираются ключевые слова? | При одинаковой длине их правила имеют меньший индекс, чем IDENT. |
| Почему `ifx` не IF + IDENT? | Длиннейшее совпадение важнее приоритета: принимающая позиция для всего `ifx` дальше. |
| Почему `==` не два присваивания? | Сканирование продолжается после первого `=`, запоминая более длинное принятие. |
| Почему нельзя сразу выдавать токен при принятии? | Впереди может быть более длинный токен, как `==` или `ifx`. |
| Зачем last? | Это последняя допустимая граница токена перед ловушкой или EOF. |
| Зачем ловушка, если можно оставить пустой переход? | Полная таблица упрощает исполнение и минимизацию; неизвестный ввод имеет определённый переход. |
| Ловушка означает ошибку для каждого прочитанного символа? | При поиске конца токена ASCII-ловушка может означать нормальную границу. Ошибка — если не было принятия. Для non-ASCII ошибка сразу. |
| Почему ловушка непринимающая? | В ней никакое правило токена не выполнено; её принятие скрывало бы ошибки. |
| WS/COMMENT непринимающие? | Они принимающие, иначе сканер не знал бы их границу; skip запрещает только выдачу токена наружу. |
| Почему `00` нельзя просто разобрать регуляркой INT? | Целая строка не подходит под INT, но сканер токенов мог бы принять два нуля. Поэтому есть дополнительный запрет на такую границу. |
| Чем TYPE_INT отличается от INT? | TYPE_INT — ключевое слово типа `int`, INT — числовая лексема. |
| Как делятся состояния при минимизации? | Сначала по выходным правилам, затем по принадлежности переходов блокам-разделителям. |
| Почему нельзя слить два принимающих состояния разных токенов? | Даже одинаковое принятие слова не означает одинаковую категорию токена; лексеру важен выход. |
| Зачем обратная таблица? | Она позволяет находить все состояния, переходящие в выбранный блок по заданному символу. |
| Зачем меньшая половина? | Это выбор разделителей Хопкрофта, который уменьшает повторную работу. |
| Почему представитель блока допустим? | После уточнения все его состояния имеют одинаковый выход и переходят в одни и те же блоки. |
| Как доказана эквивалентность? | Обход произведения двух ДКА проверяет выход каждой достижимой пары и все их ASCII-переходы. |
| Как проверена минимальность? | Независимый алгоритм Мура разделяет все состояния результата; одинаковых классов не остаётся. |
| Почему состояний стало меньше всего на три? | Сохраняются отдельные метки всех токенов; большинство состояний нужны для различных префиксов ключевых слов. |
| Какие ограничения у регулярного подхода? | Конечный автомат не хранит неограниченную вложенность скобок; эту задачу решает парсер. |
| Зачем тесты на re, если свой парсер? | re служит только независимым эталоном в тестах; само решение строит и исполняет автоматы. |
| Почему русские комментарии вызывают ошибку? | HW1 требует ASCII для всего входа. Skip не отменяет ограничение алфавита. |
| Что не проверяет эта работа? | Структуру программы, объявления имён, типы и исполнение; это задачи следующих этапов. |
| Как передать результат в HW2/T0? | Использовать JSON-таблицу вместе с правилами и scanner_policy либо импортировать build/tokenize. |

Важно суметь нарисовать фрагменты Томпсона для `a`, `ab`, `a|b`, `a*`,
вручную найти ε-замыкание, построить несколько состояний-подмножеств и
показать хотя бы одно разбиение блока Хопкрофта.
